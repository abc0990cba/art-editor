## Pen tool: bezier handles don't persist — root cause and fix

### Root cause (confirmed in code, `src/features/canvas/use-pen-tool.hook.ts`)

Two defects in the pointerup finalization destroy handle data:

1. **Drag-created smooth point loses its handles** (the reported repro: click point 1, click-drag point 2 → curve previews live → snaps straight on release).
   - `moveAddGesture` (lines 184–215) creates `g.work` **once** with `hIn: null, hOut: null` (lines 195–198); every move computes the path *with* handles only into `ctx.pendingPath.current` (lines 210–213) and never updates `g.work`.
   - `pointerUp` (lines 381–408) then nulls `pendingPath.current` (line 387) and applies the stale handle-less `g.work` (line 391). Handles are gone; `hitPen` only hit-tests existing handles, so there is no way to recover them, and Enter commits straight segments ("not saved").
2. **Dead branch for anchor/handle/segment drags** (lines 403–406): `if (pendingPath.current)` is checked after line 387 already nulled it — unreachable. These drags rely solely on the rAF flush, so a drag finishing in the same frame as its last move loses the final position (fast handle tweaks can be dropped entirely).

Everything downstream (commit as `source.bezier` with the `d` param, undo/redo, project save/load, double-click re-edit) already preserves handles faithfully — the bug is purely that handles never survive the pointer gesture into the store.

### Fix — surgical, one file: `src/features/canvas/use-pen-tool.hook.ts`

1. `moveAddGesture`: write the computed path back into `g.work` on every move (the comment at line 59 already claims "handles updated per move" — the code just never did it), so pointerup lands the final handle state.
2. `pointerUp`: capture `pendingPath.current` into a local **before** nulling it; apply it for terminal `anchor`/`handle`/`bend` gestures. (Net ~+3 lines; the file has ~15 lines of headroom under the 400-line lint cap — verified after the change.)
